# AI 驱动的智能网页采集系统 — 设计方案（优化版）

> 本文档为 `ai_job/ai_search` 的架构与实施指南。  
> 与 `online_search`（搜索引擎问答爬虫）、`ocr`（PaddleOCR 文档识别）**并列复用、职责分离**，避免把通用采集逻辑塞进垂直场景模块。

---

## 一、目标与边界

### 1.1 要解决什么问题

用户给出 **目标网址** + **自然语言采集需求**（字段、范围、条数），系统完成：

- 必要时在**可见浏览器**中由用户完成登录/验证；
- 自动选择或按指定模式采集页面数据；
- 输出结构化 JSON（及可选 CSV/Markdown）。

### 1.2 不追求（第一版明确排除）

- 全自动破解各类验证码、行为滑块、点选九宫格；
- 任意网站「零配置、100% 成功」；
- 替代 `online_search` 的「问题 → 搜索引擎 → 多详情页」垂直流程。

### 1.3 已有资产（可直接复用）

| 模块 | 路径 | 可复用能力 |
|------|------|-----------|
| Scrapy 流水线 | `online_search/` | `custom_settings`、超时/重试/限速、请求构造、正文提取（readability + 段落回退）、CLI 与日志风格 |
| PaddleOCR | `ocr/` | `OCRSettings`、`run_ocr`、多版本结果结构兼容；扩展截图/验证码入口即可 |
| LLM 依赖 | `requirements.txt` | `langchain-ollama`；决策/解析层在 `ai_search` 内新建 |

### 1.4 技术栈

| 组件 | 职责 |
|------|------|
| **DrissionPage** | 有头/无头浏览器：导航、动态渲染、用户协同登录、会话导出 |
| **Scrapy** | 高并发 HTTP 收割（含注入 Cookie/Header 后的列表/详情批量抓） |
| **Ollama + LangChain** | 模式建议、选择器生成、主内容区裁剪后的字段解析 |
| **PaddleOCR（`ocr` 包）** | 采集中途偶发文字验证码、截图文字；非登录主路径 |

### 1.5 设计哲学

**「人机协同登录 + 机器批量收割 + LLM 辅助理解与解析」**

- 登录、扫码、短信、2FA：**默认交给用户**（有头窗口），系统只负责导出会话并接续采集。
- 公开静态页：优先 **Scrapy**，避免浏览器资源浪费。
- 需登录再批量翻页：**混合模式**（浏览器拿会话 → Scrapy 并发）。
- LLM：**先裁剪 HTML 再推理**；选择器失败要**可重试、可回退**，不迷信一次生成。

## 二、登录策略（推荐默认：人机协同）

### 2.1 为什么不用自动填账号为主路径

| 自动登录 | 用户在有头窗口中登录 |
|---------|---------------------|
| 凭证落库、合规风险 | 密码仅在本机浏览器输入 |
| 验证码/2FA/扫码难覆盖 | 用户自行完成交互 |
| 登录页改版即脚本失效 | 登录 UI 变化不影响「登完再采」 |

自动登录仅作为**可选高级能力**（内网固定测试账号等），不作为 MVP 依赖。

### 2.2 标准流程（混合模式 · 阶段 A）

```
1. 系统以 headless=False 打开目标站（或登录入口 URL）
2. 提示用户：「请在浏览器中完成登录与必要验证」
3. 用户点击 CLI/Web 的「登录完成，开始采集」或等价确认
   （可选辅助：检测 URL 已离开 /login、或页面出现用户头像等元素，但不能作为唯一条件）
4. 导出 session：Cookies（必需）+ 按需 localStorage 关键项 / Authorization Header
5. 持久化到 ai_search/sessions/{site_id}.json（仅本机、可设过期；日志禁止打印 Cookie 全文）
6. 进入阶段 B：Scrapy 注入会话，高并发采集
```

### 2.3 会话复用与失效

- 新任务同站优先加载已有 `sessions/{site_id}.json`；
- 请求返回 401/403 或跳转登录页 → 提示用户重新打开窗口登录；
- 多账号：第一版限定 **单任务单浏览器 profile**，后续再扩展。

## 三、三种工作模式

### 模式一：DrissionPage 模式（浏览器模式）

**适用**：强 JS 渲染、必须在浏览器内操作才能看到的数据、单页少量抓取、登录后仍需在页内点击/滚动。

**流程**：

1. 启动浏览器（需登录时强制有头）
2. 若 `require_login`：走 [§二 人机协同登录]
3. 裁剪 DOM / 主内容 HTML → LLM 生成 CSS/XPath/文本选择器（带执行校验与重试）
4. 提取数据或导出中间 HTML → 内容解析器
5. 结束关闭浏览器（或保留会话供下次混合模式使用）

### 模式二：Scrapy 模式（HTTP 收割模式）

**适用**：静态 HTML、公开 API、**已具备有效会话**的列表/详情批量抓取。

**流程**：

1. 加载任务参数与可选 session 文件
2. 并发请求（复用 `online_search` 风格的 settings：超时、重试、AutoThrottle）
3. 正文优先 **readability-lxml + BeautifulSoup 回退**（与 `search_answer_extractors` 同思路）
4. 字段级需求：对裁剪后的 HTML 片段调用 LLM 解析 → JSON
5. 聚合、去重、输出

**说明**：相对纯浏览器的性能提升取决于站点与并发配置，文档不再写死「8–12 倍」，以实测为准。

### 模式三：混合模式（推荐 · 需登录站点的默认）

**适用**：先登录一次，再大规模翻页/列表采集（生产最常见）。

**流程**：

1. **阶段 A（DrissionPage）**：有头窗口 + 用户登录 → 导出 session
2. **阶段 B（Scrapy）**：注入 Cookies/Headers → 关闭或最小化浏览器 → 并发采集
3. 采集中途若再遇验证码：优先提示用户回到浏览器处理；可选调用 `ocr` 处理简单文字验证码

**重要实现说明**：  
`DrissionPage.change_mode()` 解决的是 **同一对象内** 的请求模式切换；本方案中 Scrapy 为**独立进程/引擎**，混合模式必须实现明确的 **Session 导出协议**（JSON：cookies、user_agent、必要 headers），而非假设一行 API 即可完成切换。

## 四、AI 核心角色（含失败处理）

### 角色一：模式调度器（后期 · auto 模式）

**职责**：在 `manual` 调试稳定后，根据任务特征**建议**模式（用户可覆盖）。

**输入信号**（加权判断，不单靠 URL 关键词）：

- 用户是否声明需要登录 / 是否提供 session 文件
- 试请求是否 401/403 或明显登录页
- 页面是否依赖 JS（可选：无头/有头各请求一次对比）
- 采集规模（单页 vs 多页列表）

**输出**：`drission` | `scrapy` | `hybrid`（默认需登录且无 session → `hybrid`）

**原则**：MVP 阶段 **默认 `manual` 指定模式**；auto 放在实施后期。

### 角色二：元素定位器（自然语言 → 可执行选择器）

**职责**：将用户对元素/列表的描述转为 CSS/XPath，供 DrissionPage 或 Scrapy 使用。

**流程**：

1. 输入自然语言 + **裁剪后的 DOM**（限制 token，去掉 script/style）
2. Ollama 生成选择器（优先 CSS，XPath 备选）
3. **执行校验**：能否唯一定位、能否取到非空文本；失败则重生成（最多 N 次，如 3）
4. 仍失败 → 降级：让用户在浏览器中**点选元素**记录选择器（可选二期）

**原则**：选择器可缓存到任务目录，同站改版后再失效重算。

### 角色三：内容解析器（HTML 片段 → 结构化 JSON）

**职责**：按字段需求从页面内容提取结构化数据。

**流程**（两级，控制成本）：

1. **规则层**：readability 提主内容 + 表格/列表常用选择器
2. **LLM 层**：仅对主内容片段 + 用户字段说明做解析；禁止整页原始 HTML 直入模型
3. 列表页：优先 LLM 生成 **列表项选择器 + 字段映射**，由 Scrapy 批量执行（可复用、可调试）

**原则**：一次性小任务可 LLM 直出 JSON；多页任务必须 **规则/选择器 + Scrapy 批量**。

### 角色四：验证码协助（降级，非主路径）

登录阶段由用户处理；采集中途偶发验证码：

1. 截图 → `ocr.run_ocr` 识别简单文字验证码
2. 失败 → 提示用户在有头窗口手动完成，或暂停任务
3. 复杂语义验证码 / 行为滑块：**不承诺自动破解**；记录失败原因供运维

## 五、验证码与视觉（务实定位）

| 场景 | 策略 |
|------|------|
| 登录页验证码 | **用户在有头窗口完成**（主路径） |
| 采集中简单文字验证码 | `ocr` 模块 + 图像预处理（二期） |
| 滑块/点选/行为检测 | 不纳入 MVP；勿依赖 PaddleOCR「攻坚」 |
| 极少数复杂图 | 可选本地视觉模型兜底（效果需实测，非承诺项） |

`ocr` 当前主攻文档/简历；扩展时在 `ai_search` 增加薄封装（截图路径/bytes → `run_ocr`），不修改 `ocr` 核心语义。

## 七、与 `online_search` 的关系

| 维度 | `online_search` | `ai_search` |
|------|-----------------|-------------|
| 场景 | 用户问题 → 搜索引擎 → TOP-K 详情 | 用户指定 URL/站点 → 按需求采集 |
| 解析 | 固定百度/DDG 解析器 | LLM + 规则动态生成 |
| 登录 | 无 | 人机协同 + session |
| 共享 | Scrapy settings 模式、extractor 思路、日志 STEP 编号风格 | 不合并 Spider 类 |

## 八、实施步骤（分阶段 · 可验收）

### 阶段 0：骨架与契约（约 1 周）

- [ ] 创建 `ai_search/` 目录与 `Task` / `Result` / `SessionSnapshot` 模型
- [ ] `session_store`：保存/加载/过期检测
- [ ] CLI 骨架：`--url --prompt --mode hybrid|scrapy|drission --require-login`
- [ ] 依赖：`DrissionPage` 写入 `requirements.txt`（当前未安装）

**验收**：能创建任务、读写空 session 文件。

### 阶段 1：人机协同混合模式 MVP（约 2–3 周）— **最高优先级**

- [ ] DrissionPage 有头打开 URL，等待用户确认「登录完成」
- [ ] 导出 Cookies → `sessions/{site_id}.json`
- [ ] Scrapy Spider 注入 session，抓取 1 个列表页 + N 个详情页（硬编码或手工配置选择器亦可）
- [ ] 正文提取复用 readability 思路
- [ ] 在 1–2 个试点站（需登录后台列表类）端到端跑通

**验收**：用户登录一次后，无需再次输入密码即可批量出 JSON。

### 阶段 2：LLM 解析与选择器（约 2 周）

- [ ] 接入 Ollama（`langchain-ollama`），主内容裁剪后再解析
- [ ] 选择器生成 + 执行校验 + 最多 3 次重试
- [ ] 列表页：生成 item 选择器，Scrapy 批量跑

**验收**：对新站点仅给自然语言字段说明，可自动出结构（允许部分字段失败并记录在 meta）。

### 阶段 3：纯 Scrapy / 纯浏览器模式（约 1–2 周）

- [ ] 公开静态站：仅 Scrapy + 规则/readability
- [ ] 强动态单页：仅 DrissionPage + LLM 解析
- [ ] session 复用与失效重新登录流程

**验收**：三种模式均可手动指定并完成典型用例。

### 阶段 4：OCR 与采集中验证码（约 1 周，可选）

- [ ] `ocr_bridge`：浏览器截图 → `run_ocr` → 回填
- [ ] 失败则暂停并提示用户

**验收**：简单文字验证码可自动一次；复杂场景友好失败。

### 阶段 5：auto 模式与生产加固（约 2 周）

- [ ] 模式调度器（建议而非强制）
- [ ] 并发/延迟/重试策略与 `online_search` 对齐并调参
- [ ] 任务日志、敏感信息脱敏、结果去重
- [ ] 2–3 类站点回归（电商列表、新闻列表、需登录后台）

**验收**：`--mode auto` 在测试集上建议准确率可接受；失败可回退 manual。

## 九、关键设计决策

| 决策 | 替代方案 | 选择原因 |
|------|---------|---------|
| **人机协同登录为默认** | LLM/脚本自动登录 | 成功率高、无密码存储、覆盖 2FA/扫码 |
| 混合模式用 **Session JSON 桥接** DrissionPage 与 Scrapy | 假设 `change_mode()` 包办一切 | 两引擎独立，协议清晰、可测试 |
| 正文先 **readability 裁剪** 再 LLM | 整页 HTML 送模型 | 降 token、提稳定性 |
| **选择器 + 批量** 与 **LLM 直出 JSON** 组合 | 只用其一 | 多页可复用、单页可快速 |
| 复用 `online_search` / `ocr` | 从零写 Scrapy/OCR | 减重复、边界清晰 |
| auto 模式放后期 | 一开始全自动 | 先 manual 跑通，降低调试难度 |
| 本地 Ollama 为主 | 仅云端 API | 隐私与成本；云端可作为配置项扩展 |

## 十、预期体验（MVP vs 完整版）

### MVP（阶段 1–2 完成后）

1. 用户：`--url https://example.com/admin/orders --prompt "订单号、金额、状态" --mode hybrid --require-login`
2. 弹出浏览器 → 用户登录 → 回车或点「开始采集」
3. 系统导出 session，Scrapy 翻页抓取，LLM 解析字段
4. 输出 `result.json` + `meta.json`（耗时、条数、是否复用 session）

### 完整版（阶段 5 完成后）

- 支持 `--mode auto`、session 自动复用与失效重登
- 公开页自动走 Scrapy；动态单页走 DrissionPage
- 用户主要提供 URL 和需求；模式与登录方式由系统建议，**可随时手动覆盖**

---

## 十一、风险与对策

| 风险 | 对策 |
|------|------|
| LLM 选择器不稳定 | 执行校验 + 重试 + 缓存；二期点选降级 |
| 仅 Cookie 不够（JWT 在 localStorage） | SessionSnapshot 扩展 storage 字段 |
| 会话过期 | 检测 401/登录跳转 → 提示重新有头登录 |
| 验证码 arms race | 登录交给用户；OCR 仅作补充 |
| 与 `online_search` 耦合 | 只共享模式与工具函数，Spider 独立 |

---

本方案在保留「浏览器 + Scrapy + 本地 LLM + OCR」完整图景的同时，**以人机协同登录和混合模式 MVP 为最先交付路径**，并与仓库内已有模块对齐，便于分阶段验收与迭代。
